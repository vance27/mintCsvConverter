# Receipt-level fields become editable, with a preserved printedTotal reference for post-edit verification

`Receipt.storeId`/`payerId`/`purchaseDate`/`tax`/`cardAmount` are all written once, inside `ingest.ts`'s `EXTRACTED` transaction, and never revisited. A wrong upload-time Store/Payer pick, a misread date, a misread tax line, or a wrong tender breakdown (which makes `cardAmount` — the figure that has to match a Citi CSV transaction within a cent for Sync's auto-matching, see `tender.ts`/`matchByAmountAndStore.ts`) are all currently unrecoverable short of deleting the receipt and re-uploading it from scratch.

`subtotal`/`total` are already fully *derived*, not independently correctable: `receiptTotals.ts`'s `recomputeReceiptTotals` (added for [ADR-0009](0009-line-items-become-fully-editable.md)'s line-item editing) redefines them as `sum(current lines)` and `subtotal + tax` on every edit. That's the right definition for keeping totals internally consistent, but it has a side effect worth naming: the *original* extracted total — the one actual ground-truth fact about what the receipt physically printed — gets silently overwritten the first time any line is touched. After that, there's nothing left to check a correction against except the reviewer's own arithmetic.

Decided:

- `storeId`, `payerId`, `purchaseDate`, `tax`, and `cardAmount` all become directly editable via a new receipt-level mutation.
- Changing **Store** on a receipt that already has line items re-runs ADR-0009's `resolveItem` against the new store for every one of the receipt's (non-removed) line items — moving each `PriceObservation`, leaving each split untouched — so the receipt ends up exactly where it would if it had been uploaded under the correct store to begin with, rather than leaving `LineItem.itemId` pointing at Items scoped to a store the receipt no longer claims to be from.
- **cardAmount** becomes a direct override — one editable number — not full CRUD over `ReceiptTender` rows. `ReceiptTender` exists purely to derive this one figure (`tender.ts`'s `cardAmount()`); the reviewer's actual goal is always "this needs to read $X to match the CSV," not reconstructing a payment-method breakdown nothing else reads.
- A new `Receipt.printedTotal Float?` preserves the VLM's original `total` reading, separate from the now-fully-derived `total` column — populated once at ingest, itself directly correctable for the case where the VLM misread that specific digit. The review page compares the live (post-edit) `total` against `printedTotal` on every render, not just once at ingest the way `reconcile()`'s arithmetic check already does — closing the gap described above.
- This mismatch is a warning, never a submit-blocker, consistent with every existing confidence signal on this page (the `reconciled` warning from [ADR-0006](0006-persist-and-surface-reconcile-deltas.md), the store-name mismatch from [ADR-0004](0004-extracted-store-reconciliation.md)): this is a single-reviewer tool, and a hard block gets in the way exactly when the reviewer has already concluded the reference value itself, not their edits, was the mistake.
- Kept deliberately separate from the existing `reconciled` boolean/`reconcileJson`, rather than folded into it: `reconciled` answers "was the original extraction internally arithmetically self-consistent" (computed once, frozen at ingest); this new check answers "does my current, possibly-edited state still match what the receipt actually printed" (live, recomputed every render). Different questions about the same receipt, so both stay visible rather than collapsing into one signal.
