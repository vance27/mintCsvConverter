# CANCELLED becomes its own status, and terminal non-submitted receipts can be hard-deleted

> **Scope later widened** — [ADR-0008](0008-widen-deletable-receipt-statuses-to-extracted.md) extends deletability to `EXTRACTED` as well, narrowing the truly-protected line down to just `SUBMITTED`. The reasoning below for why `FAILED`/`CANCELLED` are safe to delete still holds; it just turned out not to be the final scope.

Previously, cancelling an in-flight receipt reused the `FAILED` enum value with `extractionError` set to the literal string `'Cancelled by user'`, and there was no way to remove a receipt at all — a stuck `FAILED` row could only be retried, forever. `ReceiptStatus` gains a `CANCELLED` value, distinct from `FAILED` ("the user chose to stop this" vs. "extraction itself errored out"), and a hard-delete action (`DELETE /api/receipts/:id`) becomes available, but scoped tightly: only for receipts in a terminal, non-submitted status (`FAILED` or `CANCELLED`), never `SUBMITTED`, `QUEUED`, or `EXTRACTING`.

Delete is a real row removal, not a soft-delete flag: `LineItem`/`LineItemSplit`/`ReceiptTender`/`PriceObservation` rows are only ever written inside the same transaction that lands a receipt at `EXTRACTED` (see `ingest.ts`), so a `FAILED`/`CANCELLED` receipt provably has no child rows and no learned-split history to lose — the schema's existing `onDelete: Cascade` handles it cleanly. Delete also removes the retained source PDF at `sourcePath` (`receiptStorage.ts`), since Prisma's cascade doesn't touch the filesystem.

Both `FAILED` and `CANCELLED` offer Retry *and* Delete, rather than picking one action per status. The obvious design would restrict Retry to `FAILED` only (a cancel is a deliberate stop, so why resume it?) — but in practice cancels happen for reasons other than "get rid of this" (e.g. cancelling mid-extraction while iterating on the VLM prompt, then wanting to resume the same receipt against the new prompt). Forcing a permanent choice at cancel time would mean guessing at intent the system can't actually know, so both actions stay available for both statuses.
