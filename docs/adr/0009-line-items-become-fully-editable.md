# Line items become fully editable: add, correct price/quantity/code, taxable, and a soft-deletable Remove

Today `ReceiptReviewPage` lets a reviewer rename a line's display name, correct its net price paid (which only ever adjusts `discountAmount` — the printed `unitPrice`/`quantity`/`lineTotal` stay whatever the VLM read), adjust its split, or hard-delete it (`deleteLineItem` in `lineItemReview.ts` — `prisma.lineItem.delete`, no way back). Two further gaps: `extractReceipt.ts`'s `receiptSchema` already asks the VLM for a per-line `taxable` flag (it's in the Costco prompt: "Y"/"N" → taxable) and gets it back, but nothing persists it — `LineItem` has no `taxable` column at all, so it's read and silently discarded, the same class of bug `extractedStoreName` was before [ADR-0004](0004-extracted-store-reconciliation.md). And there's no way to add a line the VLM missed entirely — only whatever it did extract is correctable.

Decided: line items become fully correctable, not just re-splittable.

- **Add.** A new endpoint creates a `LineItem` the same way `ingest.ts`'s per-item loop does — going through the same Item-resolution matching (`resolveItem`, pulled out of `ingest.ts` into its own module so both ingest and review-time mutations can call it) so a hand-added line inherits a learned `ItemSplitDefault` exactly like an extracted one, and gets its own `PriceObservation` dated to the receipt's `purchaseDate` — a hand-added line is exactly as real as an extracted one and should count toward that item's price-history trend the same way.
- **Correct unitPrice/quantity.** Recomputes `lineTotal = unitPrice × quantity` — the relationship extraction is already supposed to satisfy — and updates the line's existing `PriceObservation` in place. A corrected price with a permanently-wrong price-history entry sitting next to it would be worse than not correcting it at all.
- **Correct itemCode.** Re-runs the same `resolveItem` matching against whichever Item that code actually points to, moving the existing `PriceObservation` there too. Deliberately does *not* overwrite the line's current split with the newly-matched Item's learned default — a reviewer who already adjusted this line's split before noticing the code was wrong shouldn't have that work silently clobbered by an unrelated code fix.
- **Taxable.** Adds `LineItem.taxable Boolean?`, persisted from extraction (previously discarded), editable in review. No tax-rate computation on top of it — local tax rates vary too much to hardcode one, and for now the field exists so a reviewer can eyeball it against the printed receipt, not so the system can auto-verify it.
- **Remove becomes soft-delete.** `LineItem.removedAt DateTime?`, same shape as `ImportedTransaction.removedAt`. A removed line stays in the DB — `recomputeReceiptTotals` excludes it, its `PriceObservation` is untouched — and the review page shows it struck-through with a Restore action, instead of today's one-way `prisma.lineItem.delete`.

Add and the itemCode correction are immediate server round-trips, like today's delete already is — not deferred into the batched per-line PATCH that splits/displayName/netPrice use on Submit. Both trigger real resolution work (matching against Items, moving `PriceObservation`s) whose result the reviewer needs to see reflected — an updated provenance badge, a new price-history hint — before deciding what to do next with that line; the same reason delete already breaks the page's "no per-line save step" pattern. unitPrice/quantity/taxable stay in the existing deferred batch alongside netPrice/displayName/splits: pure value corrections with no resolution side effects, no reason to special-case them differently from the fields already there.
